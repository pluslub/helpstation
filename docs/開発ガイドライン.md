# ヘルプステーション シフト管理・予約管理システム 開発ガイドライン

- 作成日: 2026-09-11
- 前提資料: [要件定義書](./要件定義書.md)、[基本設計書](./基本設計書.md)、[技術仕様書](./技術仕様書.md)、[リポジトリ構造定義書](./リポジトリ構造定義書.md)、[ユビキタス言語定義書](./ユビキタス言語定義書.md)
- ステータス: ドラフト（レビュー前）

本書は、実装（Claude Codeによる実装を含む）を進める際に共通して守るべきコーディング規約・設計方針・テスト方針・運用ルールを定めるものである。命名規則・ディレクトリ構成そのものはリポジトリ構造定義書に譲り、本書では「どう書くか・どう進めるか」を扱う。

## 1. コーディング規約

- PHP：PSR-12に準拠する。フォーマッタは`laravel/pint`を使用し、コミット前に整形する。
- Vue：Composition API（`<script setup>`）で統一する。オプションAPIは使わない。
- JS/Vue側のフォーマットはESLint + Prettierを使用する（設定ファイルは導入時に整備、6章「保留事項」参照）。
- クラス名・テーブル名・ルート名・変数名の命名規則はリポジトリ構造定義書4章を正とし、本書では重複記載しない。
- 業務で使う用語（日本語⇔コード上の英語識別子）は必ず[ユビキタス言語定義書](./ユビキタス言語定義書.md)に従う。定義書にない新しい用語が必要になった場合は、実装前に定義書へ追記してから使う。

## 2. アーキテクチャ方針（Fat Service, Thin Controller）

- コントローラーには「リクエストを受け取り、FormRequestでバリデーションし、Serviceまたはモデルを呼び出し、Inertiaレスポンスを返す」以上のロジックを書かない。
- 複数モデルにまたがる業務ロジック（配車優先度判定、予約忘れ検知、監査ログ出力等）は`app/Services/`に集約する（技術仕様書5章・リポジトリ構造定義書2.4参照）。
- モデルにはEloquentのリレーション定義・スコープ・キャスト設定のみを置き、業務ロジックは持たせない。
- 権限判定はリポジトリ構造定義書2.7の方針（ルート単位はミドルウェア、レコード単位はPolicy）に従う。

## 3. エラーハンドリング

- 業務エラー（配車優先度による登録不可、重複予約等）はLaravelの`ValidationException`またはカスタム例外を使い、Inertiaの標準的なエラーレスポンス（バリデーションエラー表示）に載せる。
- ユーザー向けのエラーメッセージは日本語で表示する（要件定義書の各画面の「エラーメッセージを表示する」という記載に対応）。
- 例外・ログメッセージ自体（開発者向け）は日本語・英語どちらでもよいが、プロジェクト内で統一する（本プロジェクトでは日本語で統一する）。
- 想定外の例外は`storage/logs/laravel.log`（Laravel標準ログ）に出力し、監査ログ（`storage/logs/audit/`）とは分離する。

## 4. テスト方針

- **Feature Test**（`tests/Feature/`）：画面・操作単位で、要件定義書6章の受け入れ条件（例：優先度が低い予約は登録不可、担当者未定のまま申請可能等）をカバーする。
- **Unit Test**（`tests/Unit/`）：`app/Services/`配下の複雑なロジック（`VehicleAssignmentService`の優先度判定・再割当、`MissedBookingDetectionService`の検知条件）を重点的にテストする。
- 単純な一覧表示・CRUD画面は、正常系1件＋主要な異常系（権限なしアクセス等）程度の最低限のテストにとどめ、過剰なテストは書かない。
- テスト実行は`php artisan test`（リポジトリ構造定義書3章参照）。

## 5. Git・レビュー運用

- ブランチ運用・コミットメッセージ規約はリポジトリ構造定義書5章を参照する。
- 1つのPull Requestは1つの目的（1機能・1修正）に絞る。複数の無関係な変更を1つのPRにまとめない（本ドキュメント群のこれまでの運用と同様）。
- レビュー観点の例：
  - 要件定義書・基本設計書・技術仕様書と実装内容が一致しているか
  - 用語がユビキタス言語定義書と一致しているか
  - Fat Service, Thin Controllerの方針に沿っているか
  - 権限チェック（ミドルウェア／Policy）が抜けていないか
  - 監査ログ出力が必要な操作（登録・変更・削除・承認）に漏れがないか

## 6. Claude Codeを用いた開発の進め方

- 実装に着手する前に、対象機能に関連する要件定義書の該当節（6章）→基本設計書→技術仕様書→リポジトリ構造定義書の順に確認し、矛盾があればコードではなくドキュメント側の疑問点として先に解消する。
- ドキュメント自体に矛盾・抜けを見つけた場合は、実装を進める前にドキュメントを修正するPRを先に作成する（このドキュメント群で行ってきた運用と同様）。
- 1回の依頼・1つのPRで完結する粒度に作業を分割し、都度レビューを受けてからマージする。

## 7. セキュリティ上の注意事項

- 入力値のバリデーションはFormRequestで行い、コントローラー側では信頼しない。
- Bladeを使わずInertia+Vueで画面を組む場合でも、ユーザー入力をそのままHTMLとして描画しない（VueのデフォルトエスケープでXSS対策）。
- CSRF対策はLaravel標準のセッション＋CSRFトークンをそのまま利用する（Inertiaが自動的に付与）。
- SQLインジェクション対策としてEloquent／クエリビルダのパラメータバインディングを用い、生SQLの文字列結合は行わない。
- パスワードポリシー・アカウントロック・セッションタイムアウト等の認証セキュリティは技術仕様書6章の実装方針に従う。
