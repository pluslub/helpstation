# ヘルプステーション シフト管理・予約管理システム ユビキタス言語定義書

- 作成日: 2026-09-11
- 前提資料: [要件定義書](./要件定義書.md)、[基本設計書](./基本設計書.md)、[技術仕様書](./技術仕様書.md)、[リポジトリ構造定義書](./リポジトリ構造定義書.md)
- ステータス: ドラフト（レビュー前）

本書は、要件定義書等で使われている業務用語（日本語）と、コード上の識別子（テーブル名・カラム名・クラス名等）の対応関係を定義するものである。ヒアリング・要件定義・設計・実装・コードレビューのすべての場面で、ここに定めた用語・訳語を使う。新しい業務用語が必要になった場合は、実装前に本書へ追記してから使用する。

## 1. 役割・アクター

| 業務用語 | コード上の識別子 | 定義 | 参照 |
|---|---|---|---|
| 管理者 | `role = 'admin'` | シフト調整担当者。全機能の閲覧・登録・編集・削除・承認権限を持つ | 要件定義書3章 |
| 職員 | `role = 'staff'` | 利用者宅へ訪問するスタッフ。自分のシフト申請、予約の新規申請・閲覧のみ可能 | 要件定義書3章 |
| 利用者 | `Client` / `clients` | 訪問看護サービスの提供対象者。個人情報保護のため苗字のみ登録する | 要件定義書6.8.2 |

## 2. シフト関連

| 業務用語 | コード上の識別子 | 定義 | 参照 |
|---|---|---|---|
| シフト | `Shift` / `shifts` | 職員1人・対象月1件で管理する、月次のシフト申請の単位 | 技術仕様書4.8 |
| シフト詳細 | `ShiftDetail` / `shift_details` | シフトのうち日付ごとの勤務内容（始業・終業時刻、休み等） | 技術仕様書4.9 |
| 申請内容 | `applied_*`列（`applied_start_time`等） | 職員が申請した時点の内容。承認・変更後も上書きされず保持される | 基本設計書4.6 |
| 管理者変更内容 | `modified_*`列（`modified_start_time`等） | 管理者が変更した後の内容。申請内容とは別カラムで保持する | 基本設計書4.6 |
| 希望休 | `applied_desired_off` | 職員本人が希望して申請する休み。単に勤務予定がないだけの「休み」とは区別する | 要件定義書6.5.2 |
| 確定内容 | （画面表示ロジック上の概念。DB列そのものではない） | 管理者変更があれば`modified_*`、なければ`applied_*`を採用した、実際に有効な内容 | 要件定義書8.1項目11 |
| 申請（提出操作） | `shifts.submitted_at` | 職員が月内の複数日分の入力をまとめて「申請」ボタンで提出する操作。提出後は本人がその内容を変更できなくなる。「シフト申請」という言葉は機能・画面全体を指す場合にも使うが、この提出操作自体を指す場合も含め、表記は必ず「申請」に統一する（「送信」は用いない）。なお「確定」は承認（3章の「確定（承認）」）や確定内容（本表上段）とは別の意味になるため、この操作の呼び名としては使わない | 要件定義書6.5.2 |

## 3. 予約関連

| 業務用語 | コード上の識別子 | 定義 | 参照 |
|---|---|---|---|
| 予約 | `Reservation` / `reservations` | 利用者への訪問1件についての申請・確定情報 | 技術仕様書4.10 |
| 仮登録 | `status = 'provisional'` | 予約が職員により申請されたが、まだ管理者の承認を得ていない状態 | 要件定義書6.4.1 |
| 承認済み | `status = 'approved'` | 管理者が承認した後の状態 | 要件定義書6.4.1 |
| 担当者未決定の予約 | `reservation_staff.staff_id IS NULL` | 予約の担当者が空欄のまま申請された状態 | 要件定義書6.4.3 |
| 固定（定期訪問） | `fixed_start_date`、`client_fixed_days_of_week` | 利用者ごとに、決まった曜日・時刻で定期的に発生する訪問予定の設定 | 要件定義書6.8.2 |
| 利用間隔 | `interval_unit`、`interval_value` | 固定設定がない利用者向けに、前回予約からの経過期間（例：3か月後）で予約忘れを検知するための設定 | 要件定義書8.1項目4 |
| 予約忘れ検知 | `MissedBookingDetectionService` | 固定設定または利用間隔をもとに、予約が滞っている利用者を検知するバッチ処理 | 技術仕様書5.2 |

## 4. 配車・車両関連

| 業務用語 | コード上の識別子 | 定義 | 参照 |
|---|---|---|---|
| 支援内容 | `SupportType` / `support_types` | 訪問の種別（通院・居宅支援等）。配車優先度を持つ | 技術仕様書4.6 |
| 配車優先度 | `dispatch_priority` | 支援内容ごとに管理者が設定する、車両割当の優先順位（値が小さいほど優先度が高い） | 基本設計書4.4 |
| 車両 | `Vehicle` / `vehicles` | 介護専用車両（電動／手動）・普通社用車。私用車はレコードを持たない | 技術仕様書4.7 |
| 使用不可フラグ | `is_unavailable` | 点検・故障等で一時的に使用できない状態を示すフラグ。空き判定の合算台数から除外する | 要件定義書6.8.4 |
| 車両プール | （概念上の用語） | 空き判定・優先度判定・再割当を行う単位。介護専用車両と普通社用車は別々のプールとして扱う | 要件定義書8.1項目30 |
| 配車優先度・車両空き判定 | `VehicleAssignmentService` | 車両プールごとの空き判定、優先度に基づく再割当を行う業務ロジック | 技術仕様書5.1 |
| 配車再割当 | `vehicle_reassigned_flag` | 優先度の高い予約のために既存予約から車両を外し、別の予約へ付け替えたことを示すフラグ | 基本設計書4.7 |

## 5. マスタ管理・削除関連

| 業務用語 | コード上の識別子 | 定義 | 参照 |
|---|---|---|---|
| マスタ | `Staff`／`Client`／`SupportType`／`Vehicle`の各モデル | 職員・利用者・支援内容・車両の基本情報を管理する対象の総称 | 要件定義書6.8 |
| 論理削除 | `deleted_at`（`SoftDeletes`トレイト） | マスタの削除操作で物理削除を行わず、一覧・選択肢からのみ除外する方式。既存のシフト・予約からの参照を保持する | 要件定義書8.1項目26 |
| 削除済み一覧 | `GET /{resource}/trashed`（`onlyTrashed()`） | 論理削除されたレコードのみを表示する一覧画面 | 要件定義書8.1項目34 |
| 復元 | `POST /{resource}/{id}/restore`（`restore()`） | 削除済み一覧から`deleted_at`をNULLに戻し、マスタを有効な状態に戻す操作 | 要件定義書8.1項目34 |

## 6. システム基盤・非機能関連

| 業務用語 | コード上の識別子 | 定義 | 参照 |
|---|---|---|---|
| 監査ログ | `AuditLogger`、`storage/logs/audit/` | 登録・変更・削除・承認操作をID・時間・操作内容とともにテキストファイルへ記録する仕組み | 技術仕様書5.3 |
| アカウントロック | `failed_login_count`、`locked_until`、`last_failed_login_at` | 連続ログイン失敗5回でログインを一定時間拒否する仕組み | 技術仕様書6章 |
| シフト未申請アラート | （ログイン時の動的判定、DB保存なし） | 翌月分のシフトが未申請の職員へ、締切5日前から表示するアラート | 要件定義書6.2 |
| シフト未承認アラート | 同上 | 未承認のシフトがある場合に管理者へ表示するアラート | 要件定義書6.2 |
| 予約未承認アラート | 同上 | 未承認の予約がある場合に管理者へ表示するアラート | 要件定義書6.2 |

## 7. 用語運用ルール

- 同じ概念を指す言葉を、ドキュメントやコードごとに違う言い方で書かない（例：「削除済みレコードの復元」と「論理削除の取り消し」のような表記ゆれを避け、常に「復元」で統一する）。
- 英語識別子は基本的にLaravelの標準命名規則（テーブル名は複数形スネークケース、モデル名は単数形アッパーキャメルケース）に従う（リポジトリ構造定義書4章参照）。
- 本書に載っていない業務用語を新たに使う必要が生じた場合は、実装・ドキュメント執筆の前に本書へ追記する。
