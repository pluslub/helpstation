# ヘルプステーション シフト管理・予約管理システム 環境構築手順書

- 作成日: 2026-09-15
- 前提資料: [技術仕様書](./技術仕様書.md)（1章の技術スタックを前提とする）、[CLAUDE.md](../CLAUDE.md)（開発環境・サーバーに必要な環境の一覧）
- ステータス: Xserver（本番）のMariaDB 10.11系固定に合わせ、Ubuntu 24.04・MariaDB 10.11.19に変更（2026-09-18）。各コマンドを1行ずつコピーできるよう、コードブロックを1コマンド1ブロックに分割（2026-09-18）。Ubuntu 24.04標準リポジトリにはPHP 8.5系が存在しないことが判明したため、`ppa:ondrej/php`を追加する手順に変更（2026-09-18）

本書は、環境ごとの構築手順を、実際に実行する順番でまとめたものである。サーバーに必要な環境の一覧は CLAUDE.md を参照。コードブロックは1つにつき1コマンドとしているため、ブロック右上のコピーボタンでそのままターミナルに貼り付けて実行できる。

- **テストサーバー**：Ubuntu（自前サーバー）。以下「1. テストサーバー環境構築」を参照。
- **開発環境**：Windows（各開発者のPC）。WSL2上にUbuntuを導入して構築する（下記「2. 開発環境構築」参照）。
- **本番環境**：Xserver（共有ホスティング、root権限なし）。テストサーバー・開発環境とは別物で、デプロイ手順も異なる（下記「3. 本番環境（Xserver）へのデプロイ手順」参照）。

テストサーバー・開発環境はどちらもUbuntu上に同じソフトウェア（PHP 8.5系・Composer 2.10.3・Node.js 24系・MariaDB 10.11.19・Git）を導入する。パッケージ導入・インストール確認のコマンドは「1. テストサーバー環境構築」側に記載し、「2. 開発環境構築」側は同じ内容を参照する形にして重複を避けている。

`.env`はGit管理対象外（リポジトリ構造定義書1.1参照）のため、`git clone`してもコピーされない。そのため、テストサーバー（山本・奥野それぞれの`~/projects/helpstation`）・WSL2（山本・奥野それぞれのPC）・Xserver（本番）の**環境ごとに、個別に`cp .env.example .env`から設定し直す**必要がある。DB接続情報（`DB_DATABASE=xs888688_helpstationtna`等）はテストサーバーとWSL2で共通の値を使うが、`.env`ファイル自体はコピーされないため、それぞれの環境で改めて設定する。

## 1. テストサーバー環境構築（Ubuntu）

物理ホスト（Ubuntu 26.04、ホスト名`pluslabo-System-Product-Name`）はUbuntu標準のツールではOSのダウングレードができないため（`do-release-upgrade`は新しいバージョンへのアップグレードのみ対応）、実際のテストサーバーは、この物理ホスト上にKVM/QEMU + libvirtで作成したUbuntu 24.04の仮想マシン（ホスト名`helpstation-testservervm`）として構築している。以下「1.1 前提」以降の手順は、この仮想マシン内で実行する。

**仮想マシンの作成方法**（再作成が必要になった場合のために記録）：

物理ホストに仮想化パッケージを導入する。

```bash
sudo apt install -y qemu-system-x86 libvirt-daemon-system libvirt-clients virtinst bridge-utils
```

自分のユーザーを`libvirt`・`kvm`グループに追加する（`sudo`無しでVM操作できるようにするため。反映にはログアウト・再ログインが必要）。

```bash
sudo usermod -aG libvirt,kvm <ユーザー名>
```

Ubuntu 24.04 Server ISOの最新ファイル名を確認する。

```bash
curl -s https://releases.ubuntu.com/24.04/ | grep -oP 'ubuntu-24\.04\.\d+-live-server-amd64\.iso' | sort -u
```

表示された最新のファイル名で、ISOを`/var/lib/libvirt/images/`に直接ダウンロードする（`libvirt-qemu`ユーザーがアクセスできる場所に置く必要があり、ホームディレクトリ配下に置くと権限エラーになる）。

```bash
sudo wget https://releases.ubuntu.com/24.04/<確認したファイル名> -P /var/lib/libvirt/images/
```

VMを作成する（例はCPU 8コア・メモリ8GB・ディスク60GB）。`--location`でISO内のカーネル・initrdの場所（`casper/vmlinuz`・`casper/initrd`）を明示的に指定しないと「インストールツリーに対応するカーネルが見つかりませんでした」というエラーになる。

```bash
virt-install --name helpstation-testserver --vcpus 8 --memory 8192 --disk path=/var/lib/libvirt/images/helpstation-testserver.qcow2,size=60 --location /var/lib/libvirt/images/<確認したファイル名>,kernel=casper/vmlinuz,initrd=casper/initrd --network network=default --graphics none --console pty,target_type=serial --extra-args "console=ttyS0,115200n8 serial" --os-variant ubuntu24.04
```

インストーラーがシリアルコンソールに表示されるが、日本語・色付き表示が文字化けするため「View SSH instructions」を選び、表示された`ssh installer@<VMのNAT内IP>`に物理ホスト内の別ターミナルから接続してインストールを進めるとよい。**「Install OpenSSH server」は初期状態で未チェックのため、必ずチェックを入れること**（忘れるとインストール後にSSH接続できなくなる）。

インストール完了後、VM内でTailscaleを導入し、独自のTailscale IPでネットワークに参加させる。

```bash
curl -fsSL https://tailscale.com/install.sh | sh
```

```bash
sudo tailscale up
```

以降、開発者はこのVMのTailscale IP（`tailscale ip -4`で確認）へ直接SSH接続する（物理ホストを経由する必要はない）。VMの起動・停止・コンソール接続が必要な場合は、物理ホストにSSH接続した上で`virsh`コマンドを使う（例：`virsh console helpstation-testserver`、`virsh start/shutdown helpstation-testserver`）。

### 1.1 前提

- OS：Ubuntu 24.04 LTSを想定する。他のディストリビューションの場合はパッケージ名・導入方法を読み替える。（Xserver（本番）のDBがMariaDB 10.11系固定であり、10.11.19はUbuntu 26.04向けには提供されていないが24.04向けには提供されているため、24.04を採用している）
- サーバーは開発者2名（山本・奥野）で共用し、各自が個別のSSHユーザーで接続する。
- サーバーは社内に設置し、Tailscaleに参加済みである。奥野は社外から接続するため、SSH・サーバーへのアクセスは（社内LANからの直接アクセスではなく）Tailscale経由を前提とする。ルーターのポートフォワーディングは行わない。

#### 1.2.2 パッケージ導入

パッケージ一覧を更新する。

```bash
sudo apt update && sudo apt upgrade -y
```

**PHP 8.5系のインストール**：Ubuntu 24.04（noble）標準リポジトリにはPHP 8.5系が存在しないため、`ppa:ondrej/php`を追加する（このPPAはUbuntu 26.04「resolute」向けには提供されていないが、24.04「noble」では利用できることを確認済み）。

`packages.sury.org`（`ppa:ondrej/php`の将来的な統合先として案内されている）も試したが、noble向けに提供されているバージョン（`8.5.10-1+0~20260828.25+ubuntu24.04~1.gbpfea0b8`）はバージョン文字列に`~`（スナップショット版を示す記号）を含み、`ppa:ondrej/php`提供版より低いものとして扱われ、既存インストール済みパッケージへの適用が「ダウングレード」としてエラーになった。そのため現時点では`ppa:ondrej/php`を採用する。

```bash
sudo add-apt-repository ppa:ondrej/php -y
```

```bash
sudo apt update
```

パッケージバージョン文字列は`ppa:ondrej/php`側の更新で随時変わるため、ハードコードせず、その場で`apt-cache madison`から取得した値をそのままインストールコマンドに使う。`php8.5-common`・`php8.5-readline`も依存関係上必要なため、同じバージョンで合わせて指定する。既に別バージョンでhold済みの場合は`--allow-change-held-packages`を付ける。

```bash
PHP_VERSION=$(apt-cache madison php8.5 | head -n1 | awk '{print $3}') && sudo apt install -y --allow-change-held-packages php8.5=$PHP_VERSION php8.5-common=$PHP_VERSION php8.5-cli=$PHP_VERSION php8.5-fpm=$PHP_VERSION php8.5-readline=$PHP_VERSION php8.5-mbstring=$PHP_VERSION php8.5-xml=$PHP_VERSION php8.5-curl=$PHP_VERSION php8.5-zip=$PHP_VERSION php8.5-mysql=$PHP_VERSION php8.5-bcmath=$PHP_VERSION php8.5-gd=$PHP_VERSION php8.5-intl=$PHP_VERSION
```

apt upgrade等で意図せずバージョンがずれないよう固定する。

```bash
sudo apt-mark hold php8.5 php8.5-common php8.5-cli php8.5-fpm php8.5-readline php8.5-mbstring php8.5-xml php8.5-curl php8.5-zip php8.5-mysql php8.5-bcmath php8.5-gd php8.5-intl
```

```bash
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
```

```bash

```

**MariaDB 10.11.19のインストール**：Ubuntu標準リポジトリにはないため、MariaDB公式リポジトリを追加する（Xserver（本番）のDBが10.11系固定のため、バージョンを合わせている）。

```bash
curl -LsS https://r.mariadb.com/downloads/mariadb_repo_setup | sudo bash -s -- --mariadb-server-version=10.11.19
```

```bash
sudo apt update
```

パッケージバージョン文字列はMariaDB公式リポジトリ側の更新で随時変わるため、ハードコードせず、その場で`apt-cache madison`から取得した値をそのままインストールコマンドに使う。

```bash
MARIADB_VERSION=$(apt-cache madison mariadb-server | grep 10.11.19 | head -n1 | awk '{print $3}') && sudo apt install -y "mariadb-server=$MARIADB_VERSION"
```

```bash
sudo apt-mark hold mariadb-server
```

```bash
sudo mariadb-secure-installation
```

対話式で以下の質問が順に表示される。このプロジェクトでの推奨回答は以下の通り。

| 質問 | 意味 | 推奨回答 |
|---|---|---|
| `Enter current password for root (enter for none)` | 現在のrootパスワード入力（新規インストール直後は未設定） | そのまま**Enter**（何も入力しない） |
| `Switch to unix_socket authentication [Y/n]` | rootログインを、パスワードではなくOSのユーザー名で認証する方式に切り替えるか | **`n`**（下記【重要】参照） |
| `Change the root password? [Y/n]` | rootパスワードを設定するか | **`Y`**として、山本・奥野の2人がわかる共通パスワードを設定する |
| `Remove anonymous users? [Y/n]` | 匿名ユーザー（ユーザー名なしでログインできる初期アカウント）を削除するか | **`Y`** |
| `Disallow root login remotely?` | rootのリモート（他ホストから）ログインを禁止するか | **`Y`**（サーバー上から`mysql -u root -p`で使うだけなので問題なし） |
| `Remove test database and access to it?` | 初期状態で用意されている`test`データベースを削除するか | **`Y`** |
| `Reload privilege tables now?` | ここまでの変更を即時反映するか | **`Y`** |

**【重要】`unix_socket`認証について**：ここで`Y`を選ぶと、rootへのログインが「Linux上でrootユーザーとしてログインしている場合のみ」許可される方式に変わり、パスワードでのログインができなくなる。山本さん・奥野さんはどちらも一般ユーザー（sudo権限はあるがrootそのものではない）でSSH接続するため、`Y`にすると1.2.4の`mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS xs888688_helpstationtna;"`が使えなくなる（`sudo mysql`のような書き換えが必要になる）。手順書の記載をそのまま使えるように、**ここは`n`を選んで、パスワード認証のままにしておく**こと。

`Change the root password?`で設定したパスワードは、山本さんとも共有しておくこと（お二人ともこのrootアカウントで共有のDBスキーマ`xs888688_helpstationtna`にアクセスする想定のため）。

#### 1.2.4 DBスキーマの作成

DBスキーマ`xs888688_helpstationtna`は全開発者で共有する（開発者ごとに分けない）ため、どちらか一方が1回だけ作成すればよい（`IF NOT EXISTS`を付けているので、2人とも実行しても問題ない）。

```bash
mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS xs888688_helpstationtna;"
```

#### 1.2.5 ポート開放

`ufw`はユーザーごとの設定ではなくシステム全体に対する設定のため、どちらか一方が両方のポート分（山本：8001、奥野：8002）をまとめて実行すればよい（2人とも実行する必要はない）。tailscale0インターフェース限定であり、ルーターのポート開放は不要。

```bash
sudo ufw allow in on tailscale0 to any port 8001 proto tcp
```

```bash
sudo ufw allow in on tailscale0 to any port 8002 proto tcp
```

反映されたか確認する（`8001/tcp`・`8002/tcp`が`ALLOW`と表示されればOK）。

```bash
sudo ufw status
```

`ufw`自体が無効（何も表示されない）の場合は、以下で有効化する。

```bash
sudo ufw enable
```

#### 1.2.6 tmuxの導入

`php artisan serve`と`npm run dev`は同時に起動しっぱなしにする必要がある。さらに、SSH接続を切断する（ターミナルを閉じる）とプロセスも終了してしまうため、`tmux`を使ってSSH切断後もプロセスが動き続けるようにする。OS全体への導入のため、どちらか一方が1回だけ実行すればよい。

```bash
sudo apt install -y tmux
```

`.env`を編集し、DB接続情報を設定する。`.env.example`の初期状態は`DB_CONNECTION=sqlite`のみで他のDB関連行が無いため、以下のように変更・追記する（DBスキーマ自体は1.2.4で作成済みのものを使う）。

```bash
sed -i 's/^DB_CONNECTION=.*/DB_CONNECTION=mysql/' .env
```

```bash
echo "DB_HOST=127.0.0.1" >> .env
```

```bash
echo "DB_PORT=3306" >> .env
```

```bash
echo "DB_DATABASE=xs888688_helpstationtna" >> .env
```

```bash
echo "DB_USERNAME=root" >> .env
```

```bash
echo "DB_PASSWORD=" >> .env
```

`DB_PASSWORD`に、`mariadb-secure-installation`で設定した実際のrootパスワードを設定する（`<パスワード>`は実際の値に置き換える）。

```bash
sed -i 's/^DB_PASSWORD=.*/DB_PASSWORD=<パスワード>/' .env
```

`<割り当てポート>`は、1.4の表にある自分のポート番号（山本：8001、奥野：8002）に置き換えること。`.env`の`APP_URL`も、実際にアクセスするURL（サーバーのTailscale IP・自分のポート番号）に合わせておく。`<サーバーのTailscale IP>`はサーバー上で`tailscale ip -4`を実行して確認する。

```bash
sed -i 's#^APP_URL=.*#APP_URL=http://<サーバーのTailscale IP>:<割り当てポート>#' .env
```

設定できたか確認する。

```bash
grep "^DB_\|^APP_URL" .env
```

ここまで設定できたら、以下を実行する。

```bash
php artisan migrate --seed
```

プロジェクト作成後は、以下でLaravelのバージョンも確認できる。

```bash
php artisan --version
```

想定バージョン：Laravel 13

#### 1.3.3 開発サーバーの起動

作業するたびに実行する手順。`<割り当てポート>`は、1.4の表にある自分のポート番号に置き換えること。`--host`を明示しないとサーバー自身からしかアクセスできない点に注意。

`tmux`セッションを開始する。

```bash
tmux new -s dev
```

1つ目のウィンドウで実行する。

```bash
cd ~/projects/helpstation
```

```bash
php artisan serve --host=0.0.0.0 --port=<割り当てポート>
```

`Ctrl+b` → `c`で新しいウィンドウを作成し、2つ目のウィンドウで実行する。`--host 0.0.0.0`を付けないと、Viteの開発サーバーがサーバー自身からしかアクセスできない（`php artisan serve`の`--host=0.0.0.0`と同じ理由）。

```bash
cd ~/projects/helpstation
```

```bash
npm run dev -- --host 0.0.0.0
```

`Ctrl+b` → `d`でセッションからデタッチすると、SSHを切断してもプロセスは動き続ける。再接続してログを確認したいときは、SSH接続後に以下を実行する。

```bash
tmux attach -t dev
```

### 1.5 補足

- `.env` は開発者ごとに用意し、Git管理対象外とする（リポジトリ構造定義書1.1参照）。DB接続情報（`DB_DATABASE=xs888688_helpstationtna`等）は共通だが、`APP_URL`等は各自の値を設定する。
- 同一サーバー上で2名が同時にアクセスするため、作業ディレクトリ・`php artisan serve`使用時のポート番号は開発者ごとに分け、衝突を避ける（割り当ては上表の通り）。
- DBスキーマ`xs888688_helpstationtna`は開発者ごとに分けず共有する。そのため、一方が実行したマイグレーション・投入したテストデータはもう一方にも反映される（意図的な運用）。
- ポート開放は`ufw`を`tailscale0`インターフェースに限定することで、Tailscaleに参加していない第三者からのアクセスを防ぐ。

## 2. 開発環境構築（Windows・WSL2）

WSL2（Windows Subsystem for Linux 2）上にUbuntu 24.04を導入する。PC1台＝開発者1人のため、テストサーバー向けの手順にあるSSHユーザーの分離・Tailscale経由アクセス・ポート開放（`ufw`）は不要。

### 2.1 前提

- Windows 10（バージョン2004以降）またはWindows 11
- WSL2上でUbuntu 24.04を使用する
- CPUの仮想化機能（Intel VT-x／AMD-V）がBIOS/UEFIで有効になっていること（WSL2は仮想マシンの仕組みを利用するため必須。無効のままだとインストールコマンドが正常に完了せず、`wsl -l -v`にディストリビューションが表示されない）

### 2.2 インストール前の確認：仮想化の有効化

1. タスクマネージャー（`Ctrl+Shift+Esc`）→「パフォーマンス」タブ→「CPU」を選択し、右下の「仮想化」が「有効」になっているか確認する
2. 「無効」の場合、PCを再起動してBIOS/UEFI設定に入り（メーカーにより起動直後の`F2`・`F10`・`Del`・`Esc`等のキー）、「Advanced」等のメニューから以下を有効にする
   - Intel製CPUの場合：`Intel Virtualization Technology`（`Intel VT-x`）
   - AMD製CPUの場合：`SVM Mode`
3. 設定を保存して再起動し（多くの場合`F10`）、タスクマネージャーで「仮想化：有効」になったことを再確認してから、以下のインストール手順に進む

### 2.3 手順

#### 2.3.1 WSL2 + Ubuntuのインストール

PowerShellを管理者権限で実行する。

```powershell
wsl --install -d Ubuntu-24.04
```

インストール後、再起動を求められる場合がある。再起動しないとインストールが完了しない。

インストール確認（再起動後、PowerShellで実行する）。

```powershell
wsl -l -v
```

一覧に`Ubuntu-24.04`が表示され、STATEが`Stopped`または`Running`であればインストール成功。何も表示されない場合は、再起動が済んでいるか確認したうえで上記コマンドを再実行する。

初回起動時、WSL内Ubuntuのユーザー名・パスワードを設定する。以降はWSL内のUbuntuターミナルで実行する。

#### 2.3.2 パッケージ導入

「1.2.2 パッケージ導入」と同じコマンドを実行する。

#### 2.3.3 インストール確認

「1.2.3 インストール確認」と同じ内容で確認する。

#### 2.3.4 リポジトリのセットアップ

`/mnt/c/`配下ではなくWSL内のLinuxファイルシステム（例：`~/projects/`）に配置すること。

- **現在地の確認**：作業フォルダで`pwd`を実行し、`/home/<ユーザー名>/...`と表示されればLinux側（OK）。`/mnt/c/Users/...`と表示された場合はWindows側に置いてしまっている。
- **やり方**：`cd /mnt/c/...`のようにWindows側のフォルダへ移動せず、最初から自分のホームディレクトリ配下（`~/projects/`等）で`git clone`する。すでに`/mnt/c/`配下にクローン済みの場合は、Windowsのエクスプローラーで該当フォルダを削除してから、下記の手順でクローンし直す。
- **理由**：`/mnt/c/`はWindowsとLinuxの変換を挟むため、ファイルを大量に読み書きする処理（`composer install`等）が大幅に遅くなる。

`~/projects/helpstation`配下のファイルは、WindowsのエクスプローラーやVS Code（Windows側）から直接見ることはできないが、以下のUNCパスでアクセスできる（`Ubuntu-24.04`はディストリビューション名、`<ユーザー名>`はWSL内で設定したユーザー名）。

```
\\wsl.localhost\Ubuntu-24.04\home\<ユーザー名>\projects\helpstation
```

WSL内のターミナルで対象ディレクトリに移動し、以下を実行するとエクスプローラーがそのフォルダを開いた状態で起動する。

```bash
explorer.exe .
```

現在地を確認する。

```bash
pwd
```

結果が`/mnt/c/...`だった場合は、まずホームディレクトリへ移動する。

```bash
cd ~
```

DBスキーマの作成は、WSL2では各自のPC上に個別のMariaDBがあるため、テストサーバーのように「1回だけ」ではなく、各自が自分のWSL2内で実行する。名前はテストサーバーと同じ`xs888688_helpstationtna`を使う（衝突は起きないが、統一のため）。

```bash
mysql -u root -p -e "CREATE DATABASE xs888688_helpstationtna;"
```

以降（`mkdir -p ~/projects`から`php artisan --version`まで）は「1.3.2 リポジトリのセットアップ」と同じコマンドを実行する（DBスキーマの作成コマンドは上記で済んでいるため、1.3.2内の同コマンドは重複実行不要）。

#### 2.3.5 開発サーバー起動

`php artisan serve`と`npm run dev`は同時に起動したままにする必要があるため、別々のターミナル（WSLのウィンドウ／タブを2つ開く）でそれぞれ実行する。**新しく開いたターミナルはプロジェクトフォルダにいないため、それぞれ`cd`してから実行すること。**ターミナルを閉じるとプロセスも終了する点に注意（自分のPC上で完結するため、テストサーバーのような`tmux`は不要）。

1つ目のターミナルで実行する。

```bash
cd ~/projects/helpstation
```

```bash
php artisan serve
```

2つ目のターミナルで実行する。

```bash
cd ~/projects/helpstation
```

```bash
npm run dev
```

### 2.4 エディタ連携

#### VS Codeの導入

- [公式サイト](https://code.visualstudio.com/)からWindows版インストーラーをダウンロードして実行するか、PowerShellで以下を実行する。
  ```powershell
  winget install Microsoft.VisualStudioCode
  ```

#### WSL2との連携

1. VS Code（Windows側）の拡張機能タブから「WSL」（発行元：Microsoft、`ms-vscode-remote.remote-wsl`）をインストールする。
2. WSL内のUbuntuターミナルでプロジェクトフォルダに移動し、`code .` を実行する。初回はWSL側にVS Code Server（サーバーコンポーネント）が自動でインストールされる。
3. VS Codeが起動し、左下に緑色で `WSL: Ubuntu-24.04` と表示されていれば、WSL内のファイルに対して直接編集・ターミナル操作ができている状態。

#### PHP開発に必要な拡張機能

WSL連携後にインストールする拡張機能は、通知に従って「WSL: Ubuntu-24.04 にインストール」を選択すること（Windows側にだけ入れても、WSL側のPHP/Node環境に対しては機能しない）。

### 2.5 アクセス方法

- WSL2はlocalhostの自動転送に対応しているため、WindowsのブラウザからそのままURL`http://localhost:8000`にアクセスできる。

### 2.6 補足

- Git用のSSH鍵は、WSL内のLinux環境に別途作成する（Windows側の鍵とは別）。
- テストサーバー向けの手順と異なり、SSHユーザー作成・Tailscale経由アクセス・ポート開放（`ufw`）の設定は不要（自分のPC上で完結するため）。

## 3. 本番環境（Xserver）へのデプロイ手順

Xserverの共有ホスティング（スタンダードプラン）はroot権限を持たず、**sudoコマンドは使用できない**。以下は全て、契約者用の一般ユーザー権限の範囲内で行う手順である。

デプロイ後、Xserver上には以下のように配置される。

```
~/projects/helpstation/                  ← rsyncで転送されるプロジェクト全体（ドキュメントルートではない）
├─ app/                         Webからは非公開（アプリケーションコード）
├─ bootstrap/                   同上
├─ config/                      同上
├─ database/                    同上（マイグレーション・シーダー）
├─ resources/                   同上（Vue/Bladeのソース。ビルド前のファイル）
├─ routes/                      同上
├─ storage/                     同上（ログ・キャッシュ）
├─ vendor/                      同上（Composer依存パッケージ。rsyncで転送）
├─ public/                      ← ドキュメントルート（Webから公開されるのはここだけ）
│   ├─ index.php                全リクエストの入口（Laravelのフロントコントローラー）
│   └─ build/                   npm run buildの成果物（manifest.json・assets/）
├─ artisan
├─ composer.json / composer.lock
└─ .env                         rsyncでは転送されない。Xserver上で3.1.3の手順により個別作成する
```

`.git`・`node_modules`はrsyncで除外しているため転送されない（3.2.2参照）。`public/`以外のディレクトリは、ドキュメントルートを`~/projects/helpstation/public`に設定している（下記3.1.1参照）ため、外部から直接アクセスできない。

本章は、初めてデプロイする際に1回だけ行う**「3.1 初回セットアップ」**と、コードを更新するたびに行う**「3.2 デプロイ手順」**に分かれる。

### 3.1 初回セットアップ

Xserverへ初めてデプロイする際に1回だけ行う。2回目以降のデプロイ（3.2）では実行しない。

#### 3.1.1 前提

- サーバーパネルでPHPのバージョンを8.5.9に設定済みであること
- サーバーパネルでMySQLデータベース・ユーザーを作成済みであること（ホスト名・DB名・ユーザー名・パスワードを控えておく）
- サーバーパネルでSSH接続情報（ホスト名・ユーザー名・ポート）を確認済みであること
- プロジェクト一式は`~/projects/helpstation`に配置する（3.2.2参照）。ドキュメントルートを、公開ドメイン配下ではなく`~/projects/helpstation/public`ディレクトリに設定済みであること（サーバーパネルの「ドキュメントルート変更」機能。root権限は不要）

#### 3.1.2 Composerの導入（Xserver上で直接`composer install`する場合）

3.2.1でローカル側に`vendor/`を含めて転送済みであれば本項は不要。Xserver上で直接installしたい場合は、root権限を使わず自分のホームディレクトリ配下にComposerを導入する。Xserverへ SSH 接続後、以下を実行する（2.10.3を指定してインストール）。

```bash
curl -sS https://getcomposer.org/installer | php -- --version=2.10.3
```

```bash
mkdir -p ~/bin
```

```bash
mv composer.phar ~/bin/composer
```

```bash
chmod +x ~/bin/composer
```

```bash
echo 'export PATH="$HOME/bin:$PATH"' >> ~/.bashrc
```

```bash
source ~/.bashrc
```

```bash
composer install --no-dev --optimize-autoloader
```

#### 3.1.3 .env設定・キー生成

サーバーパネルで確認したMySQL接続情報を、Xserver上の`.env`に設定する。Xserver上で実行する。`key:generate`は初回のみ実行すること（再実行すると既存のセッション・暗号化済みデータが壊れるため、2回目以降のデプロイでは行わない）。

```bash
cp .env.example .env
```

```bash
php artisan key:generate
```

```ini
DB_HOST=<サーバーパネルで確認したホスト名>
DB_DATABASE=xs888688_helpstationtna
DB_USERNAME=<ユーザー名>
DB_PASSWORD=<パスワード>
```

#### 3.1.4 バッチ処理（cron）の設定

サーバーパネルの「Cron設定」機能から登録する（root権限は不要、ユーザーレベルのcrontabとして動作する）。

```
* * * * * php /home/<ユーザー名>/projects/helpstation/artisan schedule:run >> /dev/null 2>&1
```

### 3.2 デプロイ手順

コードを更新してXserverへ反映するたびに、この節を実行する。

#### 3.2.1 ビルド（ローカルまたはテストサーバーで実行）

Node.jsによるフロントエンドのビルドはXserver上では行わず、テストサーバーまたは開発環境（Windows・WSL2）で実行する（技術仕様書2章参照）。`composer install`・`npm install`は1.3.2／2.3.4で導入済みの前提のため、ビルドコマンドのみ実行する。

```bash
cd ~/projects/helpstation
```

```bash
npm run build
```

（注）`vendor/`を本番用に最小化して転送したい場合は、`composer install --no-dev --optimize-autoloader`を実行することもできる。ただし、これを実行するとテスト・開発用パッケージ（phpunit等）が消え、同じ環境での開発に支障が出る（1.3.2参照）。共有のテストサーバー・開発環境ではなく、ビルド専用のチェックアウトを別途用意する場合にのみ推奨する。

#### 3.2.2 Xserverへのファイル転送

sudoを使わず、SSH経由のrsyncでファイルを転送する（FTPクライアントでも可）。ビルドした環境（ローカル）で実行する。`.git`・`.env`・`node_modules`は転送しない。

`./`は「今いるディレクトリの中身」を指すため、必ずプロジェクトのルートディレクトリ（`~/projects/helpstation`。`~/projects`ではない）に`cd`してから実行すること。`public/build`（ビルド成果物）も除外リストに入っていないため、プロジェクト全体と一緒に転送される。

```bash
cd ~/projects/helpstation
```

```bash
rsync -avz --exclude='.git' --exclude='.env' --exclude='node_modules' ./ <サーバーパネルで確認したユーザー名>@<サーバーパネルで確認したSSHホスト名>:~/projects/helpstation/
```

#### 3.2.3 マイグレーション・キャッシュ最適化

いずれもLaravel（`php artisan`）コマンドのみで完結し、sudoは不要。`migrate --force`は新しいマイグレーションがあれば適用し、無ければ何もしない。キャッシュ系コマンドはコードの変更を反映するため、デプロイのたびに再実行する。

```bash
php artisan migrate --force
```

```bash
php artisan config:cache
```

```bash
php artisan route:cache
```

```bash
php artisan view:cache
```
