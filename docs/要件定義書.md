# ヘルプステーション シフト管理・予約管理システム 要件定義書

- 作成日: 2026-09-08
- 参考資料:
  - 2026/07/07 ヒアリング議事録（山本・山田）、2026/09/04 追加ヒアリング
  - フローチャート（画面遷移・処理フロー、職員/利用者/支援内容/車両マスタ含む）
  - 画面遷移（ワイヤーフレーム）資料
  - データベース設計（ER図）
- ステータス: ドラフト（レビュー前）

## 1. 背景・目的

現在、ヘルプステーション（訪問看護サービス）のシフト管理・利用者予約管理はExcelと紙運用（印刷・貼り出し・手書き修正）に依存しており、以下の問題が発生している。

- 手書き修正による伝達ミス・シフトの見落とし
- 利用者からの予約受付がメモ書きのため紛失・記入ミスが多い
- 車両ごとに対応可能な看護内容が異なるため、配車ミス（予定日時に専用車両が空いていない等）が発生
- 3〜6か月先の予約がLINEのタイムラインに埋もれて見落とされる

本システムは、シフト表と利用者予約情報をデジタル化・一元管理し、スタッフ全員が最新情報をスマートフォン・タブレットから確認できるようにすることで、これらの課題を解消することを目的とする。

## 2. 対象範囲（スコープ）

今回のシステム化対象は以下とする。

1. **認証・ログイン機能**
2. **シフト管理機能**（申請・承認ワークフロー、月次シフト表のデジタル化・全スタッフ閲覧）
3. **利用者予約管理機能**（申請・承認ワークフロー、予約受付・登録・一覧確認）
4. **配車管理機能**（フェーズ1：車両と利用者・スタッフの割当の可視化／フェーズ2：自動配車は将来検討）
5. **マスタ管理機能**（職員・利用者・支援内容・車両の登録・変更・削除）

## 3. 利用者・ロール定義

| ロール | 説明 | 権限 |
|---|---|---|
| 管理者（シフト調整担当者） | シフト・予約の承認、マスタ管理を行う | 全機能の閲覧・登録・編集・削除・承認 |
| 職員（一般スタッフ） | 利用者宅へ訪問するスタッフ | 自分のシフト申請、予約の新規申請・閲覧（承認・確定はできない） |

※ 職員は自身のシフトを「申請」できるが、確定（承認）は管理者のみが行う。確定済みシフト・予約の直接編集は管理者のみ。

## 4. 現状の課題（As-Is）

| # | 課題 | 影響 |
|---|---|---|
| 1 | シフト表を印刷・事務所掲示し、修正は手書き | 伝達ミス、シフトの見落とし |
| 2 | 利用者からの予約はメモ書きで担当者の机に置く運用 | メモの紛失・記入ミス |
| 3 | 看護内容ごとに必要車両（車いす対応車、介護専用車両、マイカー）が異なり、稼働状況の把握が手動 | 配車ミス（専用車両が予定時刻に空いていない等） |
| 4 | 3〜6か月先の予約をLINEで連絡すると、タイムラインに埋もれる | 予約の見落とし（現状は月別クリアファイルで紙運用回避） |

## 5. 改善優先順位（お客様指定）

1. **① シフト表のデジタル化（最優先）**：確定シフトを月ごとにデジタル化し、全スタッフが閲覧できるようにする（配車ミス削減の効果も期待）
2. **② 予約メモの廃止**：紙メモによる予約受付を廃止し、システム上で入力・共有する
3. **③ 自動配車（将来検討）**：利用者と車両がセットになっているケースが多いため、将来的に自動割当を検討する

※ LINE・LINE WORKSは連絡ツールとして日常的に利用されているが、タイムラインに情報が埋もれるため、シフト・予約情報の一元管理先としては使用しない（NG）。

## 6. 機能要件

### 6.1 認証・ログイン機能

- ID・パスワードでログインする。
- ログイン成功・失敗にかかわらず、以下をログとして保存する：IPアドレス、ID、時間。
- 入力値（ID・パスワード）が職員データベースと照合し正しくない場合はエラーメッセージを表示する。
- ログイン後、シフトデータ・予約データを取得し、予約一覧画面（トップ画面）を表示する。

### 6.2 ログイン後のアラート表示

- ログイン時、以下の条件でアラートを表示する。
  - **シフト未申請アラート**：当月8日以降で、翌月分のシフトが未申請の場合に表示する（シフト申請締切は毎月10日）。何日前から警告を出すかは今後決定する（要確認事項、8章参照）。
  - **シフト承認アラート**：毎月11日の始業時刻以降で、未承認のシフトがある場合に管理者へ表示する。
  - **予約承認アラート**：毎月16日の始業時刻以降で、未承認の予約がある場合に管理者へ表示する（予約申請締切は毎月15日）。
- 各職員が翌月のシフトを申請済みかどうかを一覧で表示できるようにする。

### 6.3 予約一覧画面（トップ画面）

- 全体の予定画面と個人の予定画面を切り替えられること。
  - 全体の予定画面：週単位で表示
  - 個人の予定画面：当日単位で表示。始業・終業時刻に加え、訪問予定ごとに「時間・担当者名」「訪問先（距離）・車両」を表示する（配車・車両交換の判断材料とするため）。その日が休みの職員名も一覧表示する。
- 利用者名・職員名・日付でソート・絞り込みができること。
- 職員は担当外の利用者を含め、全ての利用者・予約情報を閲覧可能とする（配車・車両交換の判断材料とするため、閲覧範囲の制限は設けない）。
- 管理者は本画面から承認画面（6.6）へ遷移できる。
- 本画面から予約申請（6.4）・シフト申請（6.5）・各種マスタ登録（6.8）へ遷移できる。
- **シフト申請と予約申請は、画面上で一目見て区別できるようにする**（誤操作・ミス防止のため、色分けやアイコン等で明確に区別する）。

### 6.4 利用者予約管理機能

#### 6.4.1 申請・承認ワークフロー

- 利用者の予約は職員が申請し、管理者が承認する。承認されるまでは「仮登録」の状態とする。
- 1件の予約に対して、担当者（職員）は複数名割り当て可能、車両は1台のみ割り当て可能（車両が不要な予約もある）。

> **✅ 解決済み（8章 項目18参照）**：予約の担当者は**複数対応が必要**と確定した。データベース設計（ER図）は現状、予約テーブルの担当者が「社員ID」1件のみ（単一の外部キー）だが、これは要件と矛盾するため、**予約と社員の中間テーブル（多対多）への設計変更が必要**。実装着手前に必ずDB設計へ反映すること。
>
> また、DB設計の予約テーブルには「備考」に相当するカラム、および予約の「仮登録／承認」状態を管理するフラグが見当たらない。これらも実装前に確認・設計反映が必要（8章 項目19・20参照）。

#### 6.4.2 空き日時検索（3パターン）

予約入力時、以下の3パターンの検索方法をサポートする。

1. **日付が先に決まっている場合**：指定日の予約状況（空き時間）を表示する。
2. **時間帯が先に決まっている場合**：その時間帯における1週間分の予約状況を表示する（起点となる日付の決め方は要検討、8章参照）。
3. **空いている日時を探す場合**：前後1日分の「職員全員の予約状況」および「介護専用車両の予約状況」を取得し、一覧表示する（介護専用車両の予約状況のみの表示で足りるかは要検討、8章参照）。

#### 6.4.3 予約申請フォーム

入力項目は以下の通り。

| 項目 | 備考 |
|---|---|
| 利用者名 | |
| 日付 | |
| 開始時刻 | |
| 終了時刻 | 入力方式は「開始時刻＋終了時刻」または「開始時刻＋作業時間（所要時間）」のいずれとするか要確認（8章参照） |
| 担当者 | 複数選択可。利用者マスタのデフォルト担当者を初期値とし、承認時に変更可能。担当者未定のまま申請可能とするかは要確認（8章参照） |
| 支援内容 | 支援内容マスタから選択。配車優先度判定に使用（6.4.4参照） |
| 車両 | 介護専用車両（電動／手動）、普通社用車、車不要　のいずれかを選択 |
| 備考 | 自由記述 |

- 画面下部に「申請」「戻る」ボタンを配置する。

#### 6.4.4 配車優先度・車両空き判定

※ 本節でいう「優先度」は、支援内容マスタに紐づく**配車（車両割当）の優先度**を指す（予約自体の優先順位や重要性を表すものではない）。

- 日時の入力値が不正な場合はエラーメッセージを表示する。
- 介護専用車両が必要な場合、空き（1台以上）があるかを確認する。
  - 空きがあればそのまま登録可能。
  - 空きがない場合、既に申請済みの予約と比較して優先度が高いかどうかを判定する。優先度が高い場合は登録可能、そうでない場合はエラーメッセージを表示する。
  - 優先度判定により新規予約が登録可能となった場合、システムが自動的に行うのは**車両の再割当のみ**（既存の低優先度予約から車両を外し、新規予約へ割り当てる）とする。予約の日時・担当者調整自体は自動化せず、担当者が手動で行う。車両を外された予約の担当者へは**アラートで通知**する。
- 担当者（職員）・利用者本人については、同一時間帯に重複する予約が既に存在する場合、**優先度に関わらず新規予約は登録できない**（エラーメッセージを表示する）。車両の空き判定（優先度によるオーバーライドあり）とは扱いが異なる点に注意。
- 配車の優先順位は支援内容マスタの登録順（優先度）に従う。画面遷移資料に基づく初期の支援内容・優先度は以下の通り（上から優先度が高い順という理解。要確認、8章参照）。
  1. 通院（病院）
  2. 通院（クリニック）
  3. 固定
  4. 重要A
  5. 重要B
  6. 重要C
  7. 居宅支援
- 登録時、以下をログとして保存する：ID、時間、予約内容。

### 6.5 シフト管理機能

#### 6.5.1 申請・承認ワークフロー

- 職員は自身のシフトを月次カレンダー形式で申請する。承認されるまでは「仮登録」の状態とする。
- 職員マスタにて曜日ごとのデフォルト勤務時間を設定できるようにし、毎月の入力の手間を減らす。ログイン職員のデフォルトシフトデータを職員データベースから取得し、初期表示する。

#### 6.5.2 シフト申請フォーム

- 月ごと・カレンダー形式で表示する。
- 当月の労働時間の合計を表示する。
- 編集内容：始業・終業時刻の変更、終日／午前／午後の希望休。終了時刻の入力方式は「開始時刻＋終了時刻」または「開始時刻＋作業時間」のいずれとするか要確認（8章参照、予約申請フォームと共通の論点）。
- 各日の変更内容は「変更」操作でいったん保存し、月内の複数日分をまとめて「申請」ボタンで一括送信する。
- **申請（送信）後は変更不可**とする。送信後に変更が必要になった場合の運用（本人による取消・再申請の可否、管理者への修正依頼等）は要確認（8章参照）。
- 申請ボタン押下時に、以下をログとして保存する：ID、時間、シフト情報（可能な範囲で）。その後シフト管理データベース・シフト詳細データベースへ登録する。

### 6.6 承認画面（シフト・予約共通）

- 管理者のみアクセス可能。
- 月単位では画面が煩雑になるため、**週単位**でシフトと予約をまとめて表示する。
- 表示対象：職員の未承認シフト、職員の承認済みシフト、担当者未決定の予約、担当者決定済みの予約。
- 予約を職員へドラッグ＆ドロップで割り当てられるようにする（担当者未決定の予約への割当を想定）。
- 操作ボタン：シフト承認、シフト編集、予約削除、予約編集、予約承認。
  - **シフト編集フォーム**：終日／午前／午後の希望休、始業・終業時刻の変更。編集内容登録時にログ（ID、時間、変更内容）を保存し、シフトデータベースを更新する。
  - **予約編集フォーム**：時刻、担当者、支援内容、車両、備考。編集内容登録時にログ（ID、時間、変更内容）を保存し、予約データベースを更新する。
  - **予約削除**：確認メッセージを表示後、削除する。削除時にログ（ID、時間）を保存する。
  - **シフト承認・予約承認**：承認操作時にログ（ID、時間）を保存する。

#### 6.6.1 UX要望（画面遷移資料より）

顧客からの画面設計上の要望を、優先度別に整理する。初期リリースのスコープに含めるかは要確認（8章参照）。

**必須（想定）**
- 予約・シフトを選択して、詳細画面を開かなくても一覧上で承認・変更できること。
- 支援内容（車両の優先度）と車両の設定を、承認画面上で素早く行えること。
- 複数のシフト・予約を選択して一括承認できること。

**できたらいいね（Nice to have）**
- 時間帯の表示を端（左右）にドラッグすることで時間変更できること。
- 担当者をドラッグ＆ドロップで割り当てできること。
- 縦スクロール・横スクロールの両方の表示パターンに対応すること。

### 6.7 配車管理機能

#### 6.7.1 車両区分（フェーズ1）

- 車両種別は以下の3種別とする（マスタ管理機能で登録・変更）。
  - 介護専用車両（車いす車：電動／手動）
  - 普通社用車
  - 私用車（マイカー、直行直帰シフトの場合）
- 車両の現有台数（例）：車いす車（電動）3台、車いす車（手動）2台、その他（普通車）3台　計8台（実際の登録・変更はマスタ管理機能で行う）。
- 車を使わない利用者も存在する（例：居宅支援の一部、遠出のため公共交通機関を利用する方）。予約申請フォームでは「車不要」を選択可能とする。
- 各車両の稼働状況（どの利用者に対して、いつ、どの職員が使用しているか）を確認できること。

> **注意（要確認事項）**：2026/07/07ヒアリングでは「車いすは電動・手動の分類は不要」とされていたが、フローチャート・画面遷移資料（車両登録一覧：車いす/電動1〜3、車いす/手動1〜2、普通車1〜3の計8台）の両方で電動・手動を区別して管理する設計になっている。資料上の証拠は「区別する」側に一致しているため、本ドラフトは電動／手動を区別する前提で記載するが、最終的な方針は顧客に確認が必要（8章参照）。

#### 6.7.2 配車の自動化（フェーズ2・将来検討）

- 利用者と車両の組み合わせパターンが固定的なケースが多いことを踏まえ、利用者情報に紐づく推奨車両を自動的にシフト・予約に反映する機能を将来的に検討する。
- 本フェーズの詳細要件は今回のスコープ外とし、フェーズ1運用後に改めて要件定義を行う。

### 6.8 マスタ管理機能

管理者のみアクセス可能。いずれのマスタも「一覧表示 → 登録／変更／削除」の共通パターンとし、登録・変更・削除時には ID・時間・（変更の場合は変更内容、登録の場合は登録内容）をログとして保存する。削除時は確認メッセージを表示したうえで実行する。

#### 6.8.1 職員登録

一覧画面（職員一覧：ID、氏名、権限〈社員／管理〉を表示）から登録・変更・削除を行う。

| 項目 | 備考 |
|---|---|
| ID・パスワード | ログイン認証に使用 |
| 氏名 | |
| 権限 | 社員／管理（3章のロール定義に対応） |
| 勤務時間 | 曜日（日〜土）ごとに始業時刻・終業時刻を設定。終日／午前／午後の指定も可能（シフト申請時のデフォルト値として利用） |
| 年間労働時間上限 | 扶養の範囲内で働きたい職員等を想定。シフト作成時の参考情報 |

#### 6.8.2 利用者登録

一覧画面（利用者一覧：氏名を表示）から登録・変更・削除を行う。

| 項目 | 備考 |
|---|---|
| 利用者氏名 | **苗字のみ入力とする（不正アクセス対策のため、フルネームは登録しない）** |
| デフォルト担当者 | 予約申請フォームの担当者初期値として使用（承認時に変更可） |
| 車いすの要否 | 要／否の2値。電動／手動の区別は利用者マスタでは持たず、車両マスタ（6.8.4）側で管理する |
| 利用間隔 | 予約忘れの検出に使用。日／週／月の単位で指定（想定利用間隔を超えて予約がない場合の検知ロジックの詳細は要検討、8章参照） |
| 固定（定期訪問） | 「固定」区分の予約がある利用者向けに、期間・曜日・訪問時刻（開始〜終了）を登録する |

#### 6.8.3 支援内容登録

一覧画面（支援内容一覧）から登録・変更・削除を行う。初期の登録項目（案）は以下の通り（6.4.4参照）。

| 項目 | 備考 |
|---|---|
| 支援内容名 | 通院（病院）、通院（クリニック）、固定、重要A、重要B、重要C、居宅支援　等 |
| 配車優先度 | 車両割当（配車）の優先順位判定に使用（6.4.4参照） |

#### 6.8.4 車両登録

一覧画面（車両一覧）から登録・変更・削除を行う。初期の登録例は以下の通り。

| 項目 | 備考 |
|---|---|
| 車両名 | 例：車いす/電動1〜3、車いす/手動1〜2、普通車1〜3（計8台） |

## 7. 非機能要件

| 項目 | 要件 |
|---|---|
| デバイス対応 | スマートフォン・タブレットのブラウザから閲覧・入力可能なこと |
| 認証 | ID・パスワードによるログイン認証。ログイン試行はIPアドレス・ID・時間をログ保存 |
| アクセス権限 | 管理者／職員の2権限（3章参照） |
| 監査ログ | シフト・予約・マスタの登録／変更／削除／承認操作について、ID・時間・操作内容をログとして保存すること |
| データ保持期間 | シフト・予約とも当年+3年分を保持・参照可能 |
| 通知・アラート | シフト未申請、シフト未承認、予約未承認のアラート（6.2参照）。予約重複時のエラー表示（6.4.4参照） |
| 画面設計 | シフト申請と予約申請を視覚的に区別できること（誤操作防止） |
| 個人情報保護 | 利用者情報は苗字のみ登録する運用とし、フルネーム等の入力は行わない（不正アクセス・情報漏えい対策） |
| 既存ツールとの関係 | LINE／LINE WORKS／メール／Excelは日常利用ツールとして残るが、シフト・予約の一元管理先としては本システムに置き換える |

## 8. 未確定・要確認事項

1. **車いす車の電動／手動分類**：ヒアリング（7/7）では「分類不要」とされた一方、フローチャート・画面遷移資料の両方で電動3台・手動2台と区別されている。資料上は「区別する」との証拠が2件あるため、本ドラフトはその前提で記載しているが、最終方針は顧客に確認が必要。
2. シフト未申請アラートを「何日前から」表示するか（フローチャートで「後で決める」と明記）。
3. 空き時間帯検索（6.4.2パターン2）における「1週間」の起点日の決め方。
4. 空いている日時を探す場合（6.4.2パターン3）に、職員全員の予約状況まで表示するか、介護専用車両の予約状況のみで足りるか。
5. 利用者の「利用間隔」に基づく予約忘れ検出の具体的な検知ロジック・アラート方法。
6. 職員の「年間労働時間上限」を超過しそうな場合に、シフト申請・承認時に警告を出すかどうか。
7. 現場での予約変更（通院利用者に多い）を、訪問スタッフがその場でシステム入力する際の操作フロー（フローチャート上は事務所内操作を想定した記載が中心のため、外出先でのオペレーションを含め要確認）。
8. 既存Excelデータの移行要否・移行範囲。
9. 車両の「普通社用車」と「私用車（マイカー）」をシステム上でどこまで区別・管理するか（フローチャートでは車両マスタに私用車の記載がない一方、予約フォームには私用車相当の選択肢がある）。
10. セキュリティ・個人情報保護要件：利用者の医療・介護情報（要配慮個人情報）を扱う上でのアクセス制御・暗号化・第三者提供時の取り扱い等の方針。
11. ~~担当者（職員）の時間重複チェックの要否~~ → **解決済み**：職員・利用者本人ともに、同時間帯の重複予約は配車優先度に関わらず登録不可（エラー表示）とする（6.4.4参照）。
12. 申請締切（シフト10日／**予約15日で確定**）超過時の運用：締切超過分をどう扱うか（強制確定、代替シフト適用、管理者による代理登録等）は引き続き要確認。
13. 予約申請フォームで担当者を未定のまま登録できるか：承認画面の「担当者未決定の予約」区分と整合させるための入力仕様。
14. ~~予約・シフトの時間入力方式~~ → **解決済み**：データベース設計に「開始時刻」「終了時刻」の両カラムが定義されているため、「開始時刻＋終了時刻」方式に確定。
15. ~~シフト申請「送信後は変更不可」の運用~~ → **概ね解決**：シフト詳細テーブルには「社員が申請した内容」（始業時刻・終業時刻・午前休／午後休／希望休フラグ・承認フラグ）と、「管理者が変更した内容」（管理者変更フラグ・変更始業時刻・変更終業時刻・変更午前休／午後休フラグ・変更承認フラグ）が別カラムで設計されている。これにより、職員が申請した内容自体は保持されたまま、管理者による変更は別データとして記録される設計であることが確認できた。この設計を前提とした画面上の見せ方（職員に「申請内容」と「管理者変更後の内容」をどう表示するか）は別途確認する。
16. 支援内容の配車優先度：画面遷移資料の一覧順（通院（病院）＞通院（クリニック）＞固定＞重要A＞重要B＞重要C＞居宅支援）がそのまま配車優先度の順という理解でよいか。
17. 承認画面のUX要望（一覧上での承認・変更、一括承認、ドラッグでの時間変更、担当者のドラッグ＆ドロップ割当、縦横スクロール対応）について、「必須」「できたらいいね」の区分と初期リリースのスコープを正式に合意する。
18. ~~【最重要】予約の担当者（社員）は単数か複数か~~ → **解決済み**：複数対応が必要と確定。データベース設計を予約と社員の中間テーブル（多対多）に変更する必要がある（6.4.1参照）。実装着手前に必ずDB設計へ反映すること。
19. 予約データに「備考」に相当するカラムがデータベース設計に見当たらない：予約申請フォーム・承認画面編集フォームの「備考」項目をデータとして保持する設計になっているか確認する。
20. 予約の「仮登録／承認」状態を管理するフラグがデータベース設計に見当たらない：シフト同様、予約にも承認状態を管理するステータス（例：仮登録フラグ、承認フラグ）が必要と考えられるため、データベース設計への反映が必要。
21. 利用者マスタに「固定（定期訪問）」の期間・曜日・訪問時刻を保持するカラムがデータベース設計に見当たらない：定期訪問をシステム上どう管理するか（利用者マスタに保持するのか、予約データとして都度生成するのか）を確認する。
22. ~~配車優先度判定により既存予約から車両が外れた場合の扱い~~ → **解決済み**：システムが自動的に行うのは車両の再割当のみ。予約自体の日時・担当者調整は自動化せず担当者が手動で行い、車両を外された予約の担当者へはアラートで通知する（6.4.4参照）。
