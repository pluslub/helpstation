## 1. 背景・目的

現在、ヘルプステーション（訪問看護サービス）のシフト管理・利用者予約管理はExcelと紙運用（印刷・貼り出し・手書き修正）に依存しており、以下の問題が発生している。

- 手書き修正による伝達ミス・シフトの見落とし
- 利用者からの予約受付がメモ書きのため紛失・記入ミスが多い
- 車両ごとに対応可能な看護内容が異なるため、配車ミス（予定日時に専用車両が空いていない等）が発生
- 3〜6か月先の予約がLINEのタイムラインに埋もれて見落とされる

本システムは、シフト表と利用者予約情報をデジタル化・一元管理し、スタッフ全員が最新情報をスマートフォン・タブレットから確認できるようにすることで、これらの課題を解消することを目的とする。

## 2. 対象範囲（スコープ）

今回のシステム化対象は以下とする。

1. 認証・ログイン機能
2. シフト管理機能（申請・承認ワークフロー、月次シフト表のデジタル化・全スタッフ閲覧）
3. 利用者予約管理機能（申請・承認ワークフロー、予約受付・登録・一覧確認）
4. 配車管理機能（フェーズ1：車両と利用者・スタッフの割当の可視化／フェーズ2：自動配車は将来検討）
5. マスタ管理機能（職員・利用者・支援内容・車両の登録・変更・削除）

## 3. 利用者・ロール定義

| ロール | 説明 | 権限 |
|---|---|---|
| 管理者（シフト調整担当者） | シフト・予約の承認、マスタ管理を行う | 全機能の閲覧・登録・編集・削除・承認 |
| 職員（一般スタッフ） | 利用者宅へ訪問するスタッフ | 自分のシフト申請、予約の新規申請・閲覧（承認・確定はできない） |

※ 職員は自身のシフトを「申請」できるが、確定（承認）は管理者のみが行う。確定済みシフト・予約の直接編集は管理者のみ。

## 4. 現状の課題（As-Is）

| # | 課題 | 影響 |
|---|---|---|
| 1 | シフト表を印刷・事務所掲示し、修正は手書き | 伝達ミス、シフトの見落とし |
| 2 | 利用者からの予約はメモ書きで担当者の机に置く運用 | メモの紛失・記入ミス |
| 3 | 看護内容ごとに必要車両（車いす対応車、介護専用車両、マイカー）が異なり、稼働状況の把握が手動 | 配車ミス（専用車両が予定時刻に空いていない等） |
| 4 | 3〜6か月先の予約をLINEで連絡すると、タイムラインに埋もれる | 予約の見落とし（現状は月別クリアファイルで紙運用回避） |

## 5. 改善優先順位（お客様指定）

1. ① シフト表のデジタル化（最優先）：確定シフトを月ごとにデジタル化し、全スタッフが閲覧できるようにする（配車ミス削減の効果も期待）
2. ② 予約メモの廃止：紙メモによる予約受付を廃止し、システム上で入力・共有する
3. ③ 自動配車（将来検討）：利用者と車両がセットになっているケースが多いため、将来的に自動割当を検討する

※ LINE・LINE WORKSは連絡ツールとして日常的に利用されているが、タイムラインに情報が埋もれるため、シフト・予約情報の一元管理先としては使用しない（NG）。

## 6. 機能要件

### 6.1 認証・ログイン機能

- ID・パスワードでログインする。2段階認証の導入は今回のスコープ外とし、将来検討とする（9章参照）。
- ログイン成功・失敗にかかわらず、以下をログとして保存する：IPアドレス、ID、時間。
- 入力値（ID・パスワード）が職員データベースと照合し正しくない場合はエラーメッセージを表示する。
- ログイン後、シフトデータ・予約データを取得し、予約一覧画面（トップ画面）を表示する。

### 6.2 ログイン後のアラート表示

- ログイン時、以下の条件でアラートを表示する。
  - **シフト未申請アラート**：当月5日以降で、翌月分のシフトが未申請の場合に表示する（シフト申請締切は毎月10日、締切5日前から表示、8.1項目22参照）。
  - **シフト承認アラート**：毎月11日の始業時刻以降で、未承認のシフトがある場合に管理者へ表示する。
  - **予約承認アラート**：毎月16日の始業時刻以降で、未承認の予約がある場合に管理者へ表示する（予約申請締切は毎月15日）。
- 各職員が翌月のシフトを申請済みかどうかを一覧で表示できるようにする。

### 6.3 予約一覧画面（トップ画面）

- 全体の予定画面と個人の予定画面を切り替えられること。
  - 全体の予定画面：週単位で表示
  - 個人の予定画面：当日単位で表示。始業・終業時刻に加え、訪問予定ごとに「時間・担当者名」「訪問先・車両」を表示する（配車・車両交換の判断材料とするため）。配車優先度判定により車両が自動変更された予約には、その旨を示す表示を行う（6.4.4・8.1項目31参照）。その日が休みの職員名も一覧表示する。
  - ※ 訪問先の「距離」表示は今回のスコープからは外す（将来、実装可能であれば追加を検討する）。
- 利用者名・職員名・日付でソート・絞り込みができること。
- 職員は担当外の利用者を含め、全ての利用者・予約情報を閲覧可能とする（配車・車両交換の判断材料とするため、閲覧範囲の制限は設けない）。
- 管理者は本画面から承認画面（6.6）へ遷移できる。
- 本画面から予約申請（6.4）・シフト申請（6.5）・各種マスタ登録（6.8）へ遷移できる。
- シフト申請と予約申請は、画面上で一目見て区別できるようにする（誤操作・ミス防止のため、色分けやアイコン等で明確に区別する）。

### 6.4 利用者予約管理機能

#### 6.4.1 申請・承認ワークフロー

- 利用者の予約は職員が申請し、管理者が承認する。承認されるまでは「仮登録」の状態とする。
- 1件の予約に対して、担当者（職員）は複数名割り当て可能、車両は1台のみ割り当て可能（車両が不要な予約もある）。
- 訪問先（外出先）での予約変更も、事務所内操作と同じ画面・フローで行う（スマートフォン・タブレットからの操作を前提とするため、外出先専用のフローは設けない、7章参照）。
- 予約申請締切（毎月15日）を過ぎても、職員は引き続き予約を申請できる（シフトと異なり申請ロックは行わない）。締切後の申請分は、既存の予約承認アラート（毎月16日始業時刻以降、6.2参照）により管理者へ承認を促す。

> **解決済み（8.1項目13参照）**：予約の担当者は複数対応が必要と確定した。データベース設計（ER図）は現状、予約テーブルの担当者が「社員ID」1件のみ（単一の外部キー）だが、これは要件と矛盾するため、予約と社員の中間テーブル（多対多）への設計変更が必要。実装着手前に必ずDB設計へ反映すること。
>
> また、DB設計の予約テーブルには「備考」に相当するカラム、および予約の「仮登録／承認」状態を管理するフラグが見当たらないため、両カラムをデータベース設計に追加する（8.1項目14・15参照）。

#### 6.4.2 空き日時検索（3パターン）

予約入力時、以下の3パターンの検索方法をサポートする。

1. **日付が先に決まっている場合**：指定日の予約状況（空き時間）を表示する。
2. **時間帯が先に決まっている場合**：その時間帯における1週間分の予約状況を表示する。**起点日は、対象利用者の「固定（定期訪問）」設定（曜日）に合わせて決定する**。固定設定がない利用者の場合は、当日を起点日とする。
3. **空いている日時を探す場合**：前後1日分の「職員全員の予約状況」および「介護専用車両の予約状況」を取得し、一覧表示する（表示範囲は本案のまま確定）。

#### 6.4.3 予約申請フォーム

入力項目は以下の通り。

| 項目 | 備考 |
|---|---|
| 利用者名 | |
| 日付 | |
| 開始時刻 | |
| 終了時刻 | 「開始時刻＋終了時刻」方式で入力する（8.1項目10参照） |
| 担当者 | 複数選択可。利用者マスタのデフォルト担当者を初期値とし、承認時に変更可能。**空欄のまま申請可能**とする（未定の場合は承認画面の「担当者未決定の予約」として扱う、6.6参照） |
| 支援内容 | 支援内容マスタから選択。配車優先度判定に使用（6.4.4参照） |
| 車両 | 介護専用車両（電動／手動）、普通社用車、私用車（直行直帰対応）、車不要　のいずれかを選択 |
| 備考 | 自由記述 |

- 画面下部に「申請」「戻る」ボタンを配置する。

#### 6.4.4 配車優先度・車両空き判定

※ 本節でいう「優先度」は、支援内容マスタに紐づく**配車（車両割当）の優先度**を指す（予約自体の優先順位や重要性を表すものではない）。

- 日時の入力値が不正な場合はエラーメッセージを表示する。
- 車両（介護専用車両・普通社用車）が必要な場合、選択された車両種別ごとに空き（1台以上）があるかを確認する。**介護専用車両は電動／手動を区別せず、介護専用車両全体を合算した台数（例：電動3台＋手動2台＝計5台）で空きの有無を判定する**。普通社用車は普通社用車の台数（例：3台）で空きの有無を判定する。車両マスタで「使用不可フラグ」が有効な車両は、いずれの種別も合算台数から除外する（6.8.4参照）。介護専用車両で実際にどちらの車両（電動／手動）を割り当てるかは、配車優先度を参考にシステムが自動的に決定する。**電動・手動の両方に空きがある場合は、電動車両を優先して割り当てる**。普通社用車は、空きのある車両の中からシステムが自動的に1台を決定する。**介護専用車両と普通社用車は別々の車両プールであり、空き判定・優先度判定・再割当は車両種別ごとに独立して行う**（8.1項目30参照）。
  - 空きがあればそのまま登録可能。
  - 空きがない場合、同じ車両種別で既に申請済みの予約と比較して優先度が高いかどうかを判定する。優先度が高い場合は登録可能、そうでない場合はエラーメッセージを表示する。
  - 優先度判定により新規予約が登録可能となった場合、システムが自動的に行うのは**同じ車両種別内での車両の再割当のみ**（既存の低優先度予約から車両を外し、新規予約へ割り当てる）とする。予約の日時・担当者調整自体は自動化せず、担当者が手動で行う。車両を外された予約の担当者へは**アラートで通知**するとともに、該当予約に配車が自動変更された旨を表示し、予約一覧画面（6.3参照）・承認画面（6.6参照）でも確認できるようにする（8.1項目31参照）。
- 担当者（職員）・利用者本人については、同一時間帯に重複する予約が既に存在する場合、**優先度に関わらず新規予約は登録できない**（エラーメッセージを表示する）。車両の空き判定（優先度によるオーバーライドあり）とは扱いが異なる点に注意。
- 配車優先度は支援内容マスタで**管理者が任意に設定・変更可能**な値とする（登録順に自動で決まるものではない）。画面遷移資料に基づく初期の支援内容・優先度（初期設定値）は以下の通り（上から優先度が高い順）。
  1. 通院（病院）
  2. 通院（クリニック）
  3. 固定
  4. 重要A
  5. 重要B
  6. 重要C
  7. 居宅支援
- 登録時、以下をログとして保存する：ID、時間、予約内容。

### 6.5 シフト管理機能

#### 6.5.1 申請・承認ワークフロー

- 職員は自身のシフトを月次カレンダー形式で申請する。承認されるまでは「仮登録」の状態とする。
- 職員マスタにて曜日ごとのデフォルト勤務時間を設定できるようにし、毎月の入力の手間を減らす。ログイン職員のデフォルトシフトデータを職員データベースから取得し、初期表示する。
- **締切超過時に自動仮登録は行わない**（8.1項目23参照）。シフト申請フォームには対象月を選択できる仕組みを設け、申請ロックは行わない。デフォルト表示月は日付に応じて自動で進めるが、未申請の過去月にも常にアクセスして申請できる。
- 申請締切（毎月10日）は、職員へのシフト登録を促す「シフト未申請アラート」および管理者へのシフト承認を促す「シフト承認アラート」（いずれも6.2参照）の通知タイミングを決めるためだけに使用し、それ以外のシステム動作（ロック・自動登録等）のトリガーとはしない。

#### 6.5.2 シフト申請フォーム

- 月ごと・カレンダー形式で表示する。対象月はプルダウン等で選択でき、未申請の月であればいつでも申請できる（デフォルト表示月は日付に応じて自動で進める）。
- 当月の労働時間の合計を表示する。
- 申請中の内容をもとに年間累計労働時間を計算し、職員マスタの「年間労働時間上限」に対する残り時間をあわせて表示する（警告表示ではなく、数値の可視化とする）。
- 編集内容：始業・終業時刻の変更（「開始時刻＋終了時刻」方式で入力する、8.1項目10参照）、終日／午前／午後の希望休。
- **「希望休」は職員本人が申請する休みであり**、単に勤務予定が入っていないだけの「休み」（デフォルト勤務時間の対象外の曜日等）とは区別する（6.6参照）。
- 各日の変更内容は「変更」操作でいったん保存し、月内の複数日分をまとめて「申請」ボタンで一括送信する。
- **申請（送信）後は変更不可**とする。送信後に変更が必要になった場合、本人による取消・再申請は行わず、管理者へ修正を依頼する（8.1項目20参照）。
- 申請ボタン押下時に、以下をログとして保存する：ID、時間、シフト情報（可能な範囲で）。その後シフト管理データベース・シフト詳細データベースへ登録する。

### 6.6 承認画面（シフト・予約共通）

- 管理者のみアクセス可能。
- 月単位では画面が煩雑になるため、週単位でシフトと予約をまとめて表示する。
- 表示対象：職員の未承認シフト、職員の承認済みシフト、担当者未決定の予約、担当者決定済みの予約。
- 職員ごとに、職員マスタの「年間労働時間上限」に対する残り労働時間を表示する（承認判断の参考情報とするため）。
- 予約を職員へドラッグ＆ドロップで割り当てられるようにする（担当者未決定の予約への割当を想定）。
- 操作ボタン：シフト承認、シフト編集、予約削除、予約編集、予約承認。
  - **シフト編集フォーム**：始業・終業時刻の変更、「休み」（勤務予定が入っていない日）の設定・解除。「希望休」は職員本人の申請による休みとして区別して表示する（管理者による変更自体は可能）。編集内容登録時にログ（ID、時間、変更内容）を保存し、シフトデータベースを更新する。
  - **予約編集フォーム**：時刻、担当者、支援内容、車両（私用車を含む）、備考。編集内容登録時にログ（ID、時間、変更内容）を保存し、予約データベースを更新する。
  - **予約削除**：確認メッセージを表示後、削除する。削除時にログ（ID、時間）を保存する。
  - **シフト承認・予約承認**：承認操作時にログ（ID、時間）を保存する。

#### 6.6.1 UX要望（画面遷移資料より）

顧客からの画面設計上の要望を、優先度別に整理する。初期リリースのスコープに含めるかは今回のリリースでは確定せず、将来検討とする（9章参照）。

**必須（想定）**
- 予約・シフトを選択して、詳細画面を開かなくても一覧上で承認・変更できること。
- 支援内容（車両の優先度）と車両の設定を、承認画面上で素早く行えること。
- 複数のシフト・予約を選択して一括承認できること。

**できたらいいね（Nice to have）**
- 時間帯の表示を端（左右）にドラッグすることで時間変更できること。
- 担当者をドラッグ＆ドロップで割り当てできること。
- 縦スクロール・横スクロールの両方の表示パターンに対応すること。

### 6.7 配車管理機能

#### 6.7.1 車両区分（フェーズ1）

- 車両種別は以下の3種別とする。このうち車両マスタでの登録・稼働状況管理・配車優先度判定の対象となるのは**介護専用車両・普通社用車の2種別**とし、私用車は対象外とする（下記参照）。
  - 介護専用車両（車いす車：電動／手動を区別して管理）
  - 普通社用車
  - 私用車（マイカー、直行直帰対応。車両マスタには登録しないが、**予約申請時の選択肢には含める**）
- 車両の現有台数（例）：車いす車（電動）3台、車いす車（手動）2台、その他（普通車）3台　計8台（私用車は含まない。実際の登録・変更はマスタ管理機能で行う）。
- 車を使わない利用者も存在する（例：居宅支援の一部、遠出のため公共交通機関を利用する方）。予約申請フォームでは「車不要」を選択可能とする。
- 各車両（介護専用車両・普通社用車）の稼働状況（どの利用者に対して、いつ、どの職員が使用しているか）を確認できること。

> **解決済み（8.1項目1参照）**：車いすの電動／手動は区別して管理する運用で確定した。
>
> **解決済み（8.1項目7参照）**：私用車は車両マスタに登録せず、稼働状況管理・配車優先度判定の対象外とする。ただし直行直帰への対応のため、予約申請フォーム・承認画面の両方で選択肢に含める（6.4.3・6.6参照）。

#### 6.7.2 配車の自動化（フェーズ2・将来検討）

- 利用者と車両の組み合わせパターンが固定的なケースが多いことを踏まえ、利用者情報に紐づく推奨車両を自動的にシフト・予約に反映する機能を将来的に検討する。
- 本フェーズの詳細要件は今回のスコープ外とし、フェーズ1運用後に改めて要件定義を行う（9章参照）。

### 6.8 マスタ管理機能

管理者のみアクセス可能。職員・利用者・車両マスタは「一覧表示 → 登録／変更」のパターンとし、**削除は行わない**（データ保持要件との整合性のため、8.1項目26参照）。支援内容マスタのみ「一覧表示 → 登録／変更／削除」のパターンとする。登録・変更・削除時には ID・時間・（変更の場合は変更内容、登録の場合は登録内容）をログとして保存する。削除時は確認メッセージを表示したうえで実行する。

11. シフト申請「送信後は変更不可」の運用（概ね解決）：シフト詳細テーブルには「社員が申請した内容」（始業時刻・終業時刻・午前休／午後休／希望休フラグ・承認フラグ）と、「管理者が変更した内容」（管理者変更フラグ・変更始業時刻・変更終業時刻・変更午前休／午後休フラグ・変更承認フラグ）が別カラムで設計されている。これにより、職員が申請した内容自体は保持されたまま、管理者による変更は別データとして記録される設計であることが確認できた。この設計を前提とした画面上の見せ方（職員に「申請内容」と「管理者変更後の内容」をどう表示するか）は別途確認する。

13. 【最重要】予約の担当者（社員）は単数か複数か：複数対応が必要と確定。データベース設計を予約と社員の中間テーブル（多対多）に変更する必要がある（6.4.1参照）。実装着手前に必ずDB設計へ反映すること。
14. 予約データに「備考」に相当するカラムがデータベース設計に見当たらない：データベース設計に備考カラムを追加する（6.4.1参照）。
15. 予約の「仮登録／承認」状態を管理するフラグがデータベース設計に見当たらない：データベース設計に承認フラグ（仮登録／承認の状態管理用）を追加する（6.4.1参照）。
16. 利用者マスタに「固定（定期訪問）」の曜日・訪問時刻を保持するカラムがデータベース設計に見当たらない：データベース設計に曜日・訪問時刻（開始〜終了）のカラムを追加する（利用者マスタ側で保持、6.8.2参照）。対象期間（開始日）の持ち方は8.1項目21参照。
17. 配車優先度判定により既存予約から車両が外れた場合の扱い：システムが自動的に行うのは車両の再割当のみ。予約自体の日時・担当者調整は自動化せず担当者が手動で行い、車両を外された予約の担当者へはアラートで通知するとともに、該当予約に配車が自動変更された旨を表示する（6.4.4参照）。
18. 利用者情報の閲覧範囲：職員は担当外を含め全利用者・予約情報を閲覧可能とする（6.3参照）。
19. 介護専用車両の空き判定における電動／手動の区別：区別せず、介護専用車両全体の合算台数で空き判定を行う。実際にどちらの車両を割り当てるかは、配車優先度を参考にシステムが自動的に決定する。両方に空きがある場合は電動車両を優先する（6.4.4参照）。
20. シフト申請「送信後は変更不可」の場合の修正方法：本人による取消・再申請は行わず、管理者への修正依頼のみとする（6.5.2参照）。
21. 「固定（定期訪問）」の対象期間の扱い：対象期間は開始日のみを保持し、開始日以降ずっと有効とする（終了日は持たない）。「利用間隔」フィールドは前回の予約からの間隔（予約忘れ検出用）を示すものであり、対象期間とは独立したフィールドとして管理する（6.8.2参照）。
22. シフト未申請アラートを「何日前から」表示するか：締切（毎月10日）の5日前、当月5日から表示する（6.2参照）。

24. 訪問先（外出先）でのオフライン対応：**今回のスコープ外とし、将来検討とする**（9章参照）。実装する場合の方式案は、直近に取得したシフト・予約データのローカルキャッシュによる閲覧、およびフォーム入力中の内容の自動下書き保存とする（Service Workerによる自動同期・競合解決等のフルオフライン対応は対象外、7章参照）。
25. セキュリティ要件（通信・保存データの暗号化）：通信経路はSSL/TLSで暗号化する。保存データ（at rest）の暗号化は不要とする（7章参照）。
26. マスタ（職員・利用者・車両）削除時のデータ整合性：削除機能は設けない。支援内容マスタのみ従来通り削除可能とする（6.8参照）。
27. 認証まわりのセキュリティ要件：中程度のセキュリティとする。パスワードポリシーは最低8文字・英数字混在を推奨し、定期的な強制変更（パスワード有効期限）は設けない。アカウントロックアウトは連続5回のログイン失敗でロックし、30分後に自動解除する。セッションタイムアウトは8時間（1営業日）とし、頻繁な再ログインを求めない（7章参照）。
28. 車両の「点検中・故障中」等、一時的な稼働停止状態の扱い：車両マスタに「使用不可フラグ」を追加し、有効な間は空き判定の合算台数から除外する（6.4.4・6.8.4参照）。
29. 監査ログを閲覧する画面の要否・仕様：アプリ内に閲覧画面は設けず、サーバ上のテキストファイルに出力する（7章参照）。
30. 普通社用車の空き判定・配車優先度の要否：介護専用車両と同様に、普通社用車（3台）についても配車優先度に基づく空き判定・再割当を行う。介護専用車両と普通社用車は別々の車両プールであり、判定・再割当は車両種別ごとに独立して行う（6.4.4参照）。
31. 配車優先度判定により車両が自動変更された場合の提示方法：担当者へのアラート通知に加え、該当予約自体にも配車が自動変更された旨を表示し、予約一覧画面・承認画面で確認できるようにする（6.3・6.4.4・6.6参照）。
32. 監査ログの保存期間：シフト・予約データと同様に当年+3年分を保持する（7章参照）。
