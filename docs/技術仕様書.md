## 2. システム構成

- クライアント（スマートフォン・タブレットのブラウザ）→ Xserver上のLaravelアプリケーション（Webサーバー＋PHP-FPM）→ MySQL、という構成とする（基本設計書1章参照）。
- フロントエンドはInertia.jsによりLaravel側のコントローラーからVueページコンポーネントへpropsを渡す方式とし、独立したREST/GraphQL APIは持たない。
- デプロイ時、ローカルまたはCI環境で`npm run build`を実行し、生成された静的アセット（`public/build`配下）とPHPコードをまとめてXserverへ反映する。Xserver上でNode.jsのビルドは行わない。

## 4. データベース物理設計

基本設計書4章の論理設計をもとに、Laravelのマイグレーション・MySQLの型に落とし込む。主キーは全テーブルで`id BIGINT UNSIGNED AUTO_INCREMENT`とする（Laravel標準）。日時カラムは特記なき限り`TIMESTAMP`。

職員・利用者・支援内容・車両の4テーブルは、いずれも関連テーブルから参照されるため物理削除はせず、Laravelの`SoftDeletes`トレイトによる論理削除で統一する（要件定義書8.1項目26参照）。一覧・選択肢の取得は既定のスコープで`deleted_at`がNULLの行のみを対象とし、既存シフト・予約からの参照（`withTrashed()`での取得）は保持する。

## 5. 主要ロジックの実装方針

### 5.1 配車優先度・車両空き判定（要件定義書6.4.4参照）

`App\Services\VehicleAssignmentService`に集約する。

1. 予約登録・変更時、選択された車両種別（福祉車両／普通社用車）ごとに、対象日時に重複する予約件数をカウントし空き判定を行う。
2. 空きがない場合、同じ車両種別内の既存予約と`support_types.dispatch_priority`を比較する。
3. 優先度が高い新規予約が登録可能な場合、既存の低優先度予約から`vehicle_id`を外し、新規予約へ割り当てる。外された予約は`vehicle_reassigned_flag`をtrueに更新し、担当者へ通知（5.4参照）する。
4. 福祉車両は電動・手動を合算した台数で判定し、実際の車両（電動／手動）の決定・両方に空きがある場合の電動優先ロジックも本サービス内で行う。

### 5.2 予約忘れ検知（要件定義書8.1項目4参照）

`App\Console\Commands\DetectMissedBookings`を作成し、Laravelのタスクスケジューラ（`routes/console.php`内の`schedule()`）で毎日1回実行する。

- 固定（定期訪問）設定がある利用者：`client_fixed_days_of_week`の曜日設定をもとに、直近の該当曜日に予約が存在するか確認する。
- 固定設定がない利用者：直近の予約日 + `interval_value`（`interval_unit`単位）を経過しても新たな予約がない場合、対象として検知する。
- 検知結果は管理者へのアラートとして、ログイン時のダッシュボード表示に反映する（6.4参照の各アラートと同じ仕組みで判定）。

### 5.3 監査ログ（要件定義書7章・8.1項目29・32・33参照）

DBテーブルは持たず、Laravelのカスタムログチャンネル（`config/logging.php`に`audit`チャンネルを追加、`daily`ドライバ）で`storage/logs/audit/audit-YYYY-MM-DD.log`へ1行1操作で出力する。

- 保持期間：`days`オプションを1500日程度（当年+3年を安全に超える日数）に設定し、自動削除が要件の保持期間を下回らないようにする。
- 出力項目：日時、職員ID（ログイン失敗時等はnull）、操作種別（login/create/update/delete/approve等）、対象テーブル名、対象レコードID、変更内容・登録内容・削除内容、IPアドレス（ログイン試行時のみ）。
- 各コントローラー・サービスの登録／変更／削除／承認処理の末尾で共通の`AuditLogger`ヘルパーを呼び出す方式とし、書き漏れを防ぐ。

### 5.4 通知・アラート（要件定義書6.2・7章参照）

常時起動の通知基盤は持たず、ログイン時・画面表示時にその都度DBを参照して判定するオンデマンド方式とする。

- シフト未申請／シフト未承認／予約未承認アラート：ログインコントローラーで判定しダッシュボードへ表示する。
- 配車自動変更の通知：5.1のサービス実行時に`vehicle_reassigned_flag`をtrueにするのと同時に、対象予約の担当者に該当する職員向けの表示要否を予約一覧画面・承認画面の描画時に判定する（常駐のプッシュ通知は行わない）。

## 6. 認証・セキュリティ実装方針（要件定義書6.1・7章参照）

- Laravel標準の認証機構（Auth）をベースに、ログインは`login_id`＋パスワードで行うカスタムガードを実装する（メールアドレス認証は使用しない）。
- パスワードは`Hash::make()`（bcrypt）で保存する。パスワードポリシーは`Illuminate\Validation\Rules\Password::min(8)->mixedCase()->numbers()->symbols()`により、最低8文字・英字（大文字・小文字）・数字・記号の混在を必須とするバリデーションルールとして実装する（要件を満たさない場合は入力を拒否する）。有効期限による強制変更は実装しない。
- アカウントロック：ログイン処理では、まず`locked_until`が現在時刻より未来かどうかを確認し、未来であればパスワード照合を行わずに即座にログインを拒否する（「アカウントがロックされています」等のエラーメッセージを表示し、`failed_login_count`・`last_failed_login_at`は更新しない）。`locked_until`が未来でない場合のみパスワード照合へ進む。ログイン失敗のたびに、`last_failed_login_at`が30分以上前（またはNULL）であれば`failed_login_count`を1にリセットし、30分以内であればインクリメントする。その後`last_failed_login_at`を現在時刻に更新する。`failed_login_count`が5に達したら`locked_until`に現在時刻+30分を設定してログインを拒否する。ログイン成功時は`failed_login_count`を0、`last_failed_login_at`・`locked_until`をNULLにリセットする。
- セッションタイムアウト：`config/session.php`の`lifetime`を480（分）に設定する。
- 通信はXserverのSSL/TLSを利用しHTTPS化する。保存データ（at rest）の暗号化は行わない（要件定義書8.1項目25参照）。
- 権限制御：ルート単位の粗い制御（承認画面・マスタ管理等、管理者専用の画面・操作全体）は、`role`が`admin`かどうかを判定するミドルウェアで行う（ロールが2種類のみのため、外部の権限管理パッケージは導入しない）。一方、シフトの編集のように「対象レコードが自分のものか」を1件単位で判定する必要がある操作は、Laravel標準の`ShiftPolicy`で判定し、コントローラーから`$this->authorize()`を呼び出す（職員は自分のシフトのみ編集可、管理者は全件可）。予約の編集・削除は職員には行わせず管理者のみ可能なため（3章・6.6参照）、`ReservationPolicy`の`update`・`delete`は所有者に関わらず管理者判定のみを行う。

4マスタのDELETEルートはいずれも物理削除ではなく、各モデルに付与した`SoftDeletes`トレイトによる論理削除（`delete()`呼び出しで`deleted_at`が設定される）を行う。各マスタ画面には「有効な一覧」（既定）と「削除済み一覧」（`GET /{resource}/trashed`、`onlyTrashed()`で取得）を切り替えるタブを設け、削除済み一覧の各行から`POST /{resource}/{id}/restore`を呼び出すことで`restore()`による復元を行う（要件定義書8.1項目34参照）。

## 8. デプロイ・運用

- デプロイ手順：①ローカル（または将来的にCI）で`composer install --no-dev --optimize-autoloader`と`npm run build`を実行、②生成物・PHPコードをXserverへrsync/FTP等で反映、③`php artisan migrate --force`でDBを更新、④`php artisan config:cache route:cache view:cache`で最適化する。
- バッチ処理：Xserverのcron機能で`* * * * * php artisan schedule:run >> /dev/null 2>&1`を登録し、Laravelのタスクスケジューラ経由で予約忘れ検知（5.2）等を実行する。
- バックアップ・冗長構成：未確定（要件定義書8.2項目2参照）。方針が決まり次第、本章に反映する。
